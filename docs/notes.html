Project orientation & codebase state

2026-05-17

Returning to the project after a break. Two execution modes exist: the eager mode (Tensor + Engine) is a legacy prototype, complete and tested but no longer the active codebase. The symbolic/compiled mode (Symbol + Compiler + Executor) is the current version.

Symbolic pipeline — what's done

  • symbol.py — full operator-overloaded graph builder, mirrors the old Tensor API
  • compiler.py — optimization pipeline: canonicalization, constant folding, add/mul flattening, algebraic simplification, dead code elimination, decanonicalization
  • Executor.py — forward execution of a compiled topo list, with selective caching

Known bugs / incomplete

  • Compiler._accumulate() — reassigns a local variable instead of mutating, so gradients never accumulate
  • Executor.forward() line 150 — if node in topo[-1] is nonsensical, will crash at runtime
  • compile_backwards() — SOFTMAX case references undefined axis variable
  • Executor — no backward() method yet, only forward

Next steps — symbolic backward pass

2026-05-17

Priority order for getting the symbolic backward pass working end-to-end:

  • 1. Fix Compiler._accumulate() — one-liner bug, but blocks everything downstream
  • 2. Fix Executor.forward() — the bad if node in topo[-1] check will crash before any backward can run
  • 3. Verify compile_backwards() end-to-end — once 1 & 2 are fixed, run the symbolic backward and diff against the eager mode as a reference oracle
  • 4. Add Executor.backward() — execute the gradient graph that compile_backwards() produces
  • 5. Tests — existing tests all target the eager mode; need equivalent coverage for the symbolic pipeline

Open design question

For step 4: does Executor.backward() treat the gradient graph as a static compiled artifact (run once, reuse), or does it recompile on each backward call? This affects how intermediate activations are stored and whether the backward graph needs its own caching strategy.
